# Build 42 recovery + main synchronization design

Date: 2026-09-06
Stable baseline: `jarvis-dev` @ `ef7c44482ec332afc51a1661dbe2c01de3078b2b` (Build 41)
Recovery branch: `recovery/build42-main-sync`
Existing draft PR: #16 `feature/build42-face-diagnostics-spotify` -> `jarvis-dev`

## Goal

Recover development after the mixed Build 42 pull request without destabilizing the last known-good Build 41 baseline, then synchronize the repository governance/agent commits from `main` into the JARVIS development line through an isolated integration branch.

This design deliberately separates responsibilities that were combined in PR #16.

## Decision 1 — Freeze PR #16

PR #16 remains open as a draft and must not be merged into `jarvis-dev`.

Its current head is `7b0fcef7fc2dc2a5d1adddc8875131bf1e13651f`. It contains two independent areas: front-camera face diagnostics and Spotify integration. Its latest known CI run fails during the device build/test-bundle compilation stage, so it is not a valid release candidate.

PR #16 is retained as historical/work-in-progress evidence while its useful changes are extracted into narrower branches.

## Decision 2 — Split Build 42 by responsibility

### Build 42A — face diagnostics

Create a new branch from the Build 41 baseline and bring over only the face-diagnostic changes required to identify the front-camera recognition failure.

Allowed scope:

- `JARVIS/Services/Vision/FaceDiagnosticSupport.swift`
- diagnostic-only changes in `FaceRecognitionService.swift`
- diagnostic-only changes in `PhoneCameraService.swift`
- corresponding face diagnostic tests
- minimal project/test registration needed for those files
- build number update only when the branch is ready to produce an IPA

Explicitly excluded:

- Spotify dependency
- Spotify URL schemes/settings/auth/token code
- Spotify tests
- unrelated audio changes
- recognition threshold or matching algorithm changes before diagnostics identify the root cause

Success criteria:

1. portable simulator tests pass;
2. device build/test-bundle compilation passes;
3. IPA is generated by CI;
4. a physical iPhone run produces enough face-pipeline diagnostics to identify the failing stage.

### Build 43 — Spotify

Spotify work moves to a separate branch based on a green `jarvis-dev` after Build 42A is resolved.

It must contain its own service/tool/settings implementation and tests. Spotify must not block face diagnostics or baseline recovery.

## Decision 3 — Treat Build 41 as the stable baseline

`jarvis-dev` remains unchanged at Build 41 while Build 42A is repaired.

Current baseline commit:

`ef7c44482ec332afc51a1661dbe2c01de3078b2b`

No force push, direct recovery commit, or merge of PR #16 is allowed against `jarvis-dev` during this process.

Before promoting any replacement Build 42 work, CI must be green and the generated IPA must be traceable to the candidate commit.

## Decision 4 — Synchronize `main` through an isolated integration branch

`main` and `jarvis-dev` are intentionally divergent. At the time of this design, `jarvis-dev` is 206 commits ahead of and 5 commits behind `main`.

The five `main`-side commits contain repository governance/agent/CI infrastructure, including the two-agent workflow, orchestrator, and secure default-branch patch dispatcher.

Do not merge `main` directly into `jarvis-dev`.

Instead:

1. use `recovery/build42-main-sync` (created from the Build 41 baseline) as the integration workspace;
2. bring the five missing `main` commits into that branch in chronological order or by an equivalent merge that preserves their final tree;
3. resolve conflicts only in the integration branch;
4. verify that the JARVIS app sources and Build 41 runtime are not unintentionally replaced by old/default-branch code;
5. run the full CI pipeline;
6. only after the integration branch is green, open a dedicated PR back to `jarvis-dev`.

Because both branches changed `.github/workflows/apply-patch.yml`, that path receives explicit conflict review. Agent documentation and governance files should be additive unless inspection proves otherwise.

## Execution order

1. Freeze PR #16 as draft and mark it as superseded by the split-recovery strategy.
2. Create Build 42A face-diagnostics branch from `ef7c444...`.
3. Extract only face-diagnostic code/tests from PR #16.
4. Diagnose and fix the exact CI failure on Build 42A using the smallest change needed.
5. Verify CI and generate an IPA.
6. Keep Spotify out of this path; recreate it later as Build 43.
7. Integrate the five missing `main` commits on `recovery/build42-main-sync`.
8. Resolve/verify workflow conflicts and run CI.
9. Open a dedicated synchronization PR to `jarvis-dev` only after green verification.

## Safety rules

- One PR = one primary responsibility.
- `jarvis-dev` is protected as the stable product line during recovery.
- No merge to `jarvis-dev` or `main` without explicit user approval.
- No force push to stable branches.
- No claim that a build is fixed until the relevant GitHub Actions run is green.
- Physical-iPhone acceptance remains required for face behavior even after CI passes.

## Expected resulting branch/PR structure

- `jarvis-dev` — Build 41 stable baseline until promotion.
- `feature/build42-face-diagnostics` — narrow Build 42A recovery PR.
- `feature/build43-spotify` — Spotify follow-up after Build 42A.
- `recovery/build42-main-sync` — isolated synchronization workspace for the five missing `main` commits.
- PR #16 — draft/superseded reference, never merged as-is.
